# Plan: JavaScript → TypeScript Migration (Pod)

Status: done
Scope: `src/`, `cloud/` ✅, `open-sse/` (frozen as JS — see Phase 9)
Goal: end state is a strictly-typed, real type system across `src/`, with `tsc --noEmit --strict` green in CI.

## Non-Negotiables

1. **No runtime behavior changes.** Every phase must end with `bun run check && bun run test:run && bun run build` green.
2. **No `// @ts-nocheck` and no `any` as an escape hatch.** `unknown` + narrowing at trust boundaries. `any` is allowed only at the FFI edges (third-party SDKs without types, Web Streams internals) and must be commented with a `todo(ts)` reason.
3. **Bun first.** Bun ships first-class TS — no separate transpile step. Use `bun --bun next build` exactly as today.
4. **Next.js 16 standalone build must keep working.** `output: "standalone"` and `serverExternalPackages: ["bun:sqlite"]` stay untouched.
5. **All 1338 tests must pass after every phase.** New type tests use vitest's built-in typecheck (`vitest --typecheck`).
6. **CI gate order**: `bun run check` → `bun run test:run` → `tsc --noEmit` → `bun run build`. `tsc` is added in Phase 1 and is the only new step.

## Tooling Additions (Phase 0, before any code changes)

Dev deps to add with `bun add -d`:

- `typescript@^5.6` — compiler.
- `@types/node@^22` — Node globals (`process`, `Buffer`, `URL`, `Request`, `Response`).
- `@types/bun@latest` — Bun globals (`Bun`, `Bun.RedisClient`, `Bun.serve`). Bun ships official types; do not roll our own.
- `@types/react@^19` and `@types/react-dom@^19` — already implicit via Next.js 16 but make them explicit so `tsc` resolves them.
- `@types/express`, `@types/express-serve-static-core`, `@types/proper-lockfile`, `@types/selfsigned`, `@types/socks-proxy-agent` — only added on first use, not preemptively.

Do **not** add: `ts-node`, `tsx`, `tsdown`, `ts-jest`, `@typescript-eslint/*`. Biome handles formatting; we don't want two linters. Bun runs TS directly. `tsdown` only makes sense if/when we ship a standalone library output — not today.

Files to create at repo root:

- `tsconfig.json` (root) — primary config, see below.
- `tsconfig.tsbuildinfo` is auto-generated next to it; gitignore it.
- `.gitignore` already excludes `.next` and `node_modules`; add `*.tsbuildinfo` if not present.

## Migration Order (leaves → roots)

Strict ordering. Do not skip ahead; do not parallelize. Each phase is its own PR.

| Phase | Scope                                                                             | Why now                                                |
| ----: | --------------------------------------------------------------------------------- | ------------------------------------------------------ |
|     0 | Tooling: `tsconfig.json`, deps, scripts                                           | Locks the baseline before code changes.                |
|     1 | Pure leaf utilities                                                               | Proves Bun + tsc + Next 16. No behavior change risk.   |
|     2 | Domain types in `src/shared/constants/`, `src/shared/utils/`, `src/shared/hooks/` | Defines vocabulary used by everything below.           |
|     3 | `src/lib/` backend services                                                       | Largest single source of type gain.                    |
|     4 | `src/app/api/**/route.js` (26 route groups)                                       | Locks HTTP request/response shapes.                    |
|     5 | `src/sse/` orchestration                                                          | Bridges typed `lib/` to untyped `open-sse/`.           |
|     6 | `src/shared/components/**` + `src/shared/store/**` + `src/app/(dashboard)/**`     | UI surface; biggest churn.                             |
|     7 | Entry points: `src/proxy.js`, `src/dashboardGuard.js`, `src/server-init.js`       | Top of the tree, depends on everything.                |
|     8 | `cloud/` (Cloudflare Worker)                                                      | Separate `tsconfig.json` + `wrangler deploy` pipeline. |
|     9 | `open-sse/` decision                                                              | Either migrate, or freeze as JS — see Phase 9.         |

## Per-Phase Procedure (apply to every phase)

For each file:

1. Rename `.js` → `.ts` (or `.jsx` → `.tsx` for components).
2. Add explicit types on exported functions first; internal helpers can stay inferred if they're not exported.
3. At trust boundaries (HTTP body, env var, JSON.parse, fs read), use `unknown` + a runtime narrowing helper. The codebase already has `parseJsonBody`, `sanitizeError`, `validateUrl` — reuse them. Do not introduce a new validation library.
4. For untyped third-party modules, create `src/types/<module>.d.ts` ambient declarations; never use `as any` to silence.
5. Run: `bun run check && bun run test:run && tsc --noEmit && bun run build`. All four must pass before opening the PR.
6. PR body lists: files touched, `any` count delta (should be 0), `unknown` count delta (should be positive), and the test run output line.

## Phase 0 — Tooling

**Goal**: install TS, write `tsconfig.json`, add `tsc` to `bun run check`, prove it runs on the unmodified JS tree.

**Scope**: no source changes. `package.json`, `tsconfig.json`, `biome.json` only.

**tsconfig strategy**: as above (`allowJs: true`, `checkJs: false`, `noEmit: true`, `strict: false`).

**Risks**:

- Biome formatter may reformat `.ts` files differently than `.js`. Verify `bun run check` (which runs `biome format --write`) still passes.
- ESLint config from `eslint-config-next` may not understand `.ts` cleanly. Test one `.ts` file early to surface issues.

**Script changes** (`package.json`):

```diff
- "check": "biome format --write . && biome lint . && bun x eslint .",
+ "check": "biome format --write . && biome lint . && bun x eslint . && bun x tsc --noEmit",
+ "typecheck": "bun x tsc --noEmit",
```

`typecheck` is a separate script so CI can run it in parallel with `test:run` if desired.

**Exit criteria**:

- `tsc --noEmit` runs in < 30s, reports 0 errors on the unmodified tree.
- `bun run check` passes.
- `bun run test:run` passes (1338 tests).
- `bun run build` succeeds (standalone output unchanged).

**Effort**: small (~30 min).

**Goal**: convert all of `src/lib/**` (except `src/lib/sqlite/`, which goes in Phase 3b).

**Scope**:

- Top-level: `localDb.js`, `cacheLayer.js`, `consoleLogBuffer.js`, `contentTypeGuard.js`, `dataDir.js`, `disabledModelsDb.js`, `initCloudSync.js`, `providerNormalization.js`, `modelsDevSync.js`, `parseJsonBody.js` (done in Phase 1), `requestDetailsDb.js`, `routeAuth.js`, `sanitizeError.js` (done in Phase 1), `semanticCache.js`, `shutdown.js`, `usageDb.js`, `validateUrl.js` (done in Phase 1), `empty-module.js` (done in Phase 1)

**tsconfig strategy**: still `checkJs: false` at the project level. Per-file `// @ts-check` is not used (we don't want ESLint-style directives scattered). Just rely on `tsc` checking the new `.ts` files.

**Type strategy**:

- `localDb.js` (1663 lines): the biggest single file. Strategy: convert the **return types** first, parameter types second. Public API surface:
  - `getSettings(): Promise<Settings>`
  - `getApiKeyByKey(key: string): Promise<ApiKey | null>`
  - `getProviderConnection(id: string): Promise<ProviderConnection | null>`
  - Plus a `Settings` type derived from the `DEFAULT_SETTINGS` shape.
  - For the 35+ consumer files, leave them as JS until they hit Phase 4. They keep working because `checkJs: false`.
- `rateLimit/backend.js`: `getBackend(): Promise<RateLimitBackend>` with `RateLimitBackend` as a structural interface. **No `instanceof` or `constructor.name` checks** in TS — keep using duck-typed method checks per AGENTS.md "Rate Limiting" rule 5. The TS type just describes the interface; the runtime check stays as `typeof backend.connect === "function"`.
- `semanticCache.js`: the `inFlightRequests` Map is `Map<string, Promise<Response>>`. The `signature` argument is computed by the caller — make it `string` at the API.
- `cacheLayer.js`: `LRUCache<K, V>` generic, where `K extends string`.
- `tunnel/cloudflared.js` and `tunnel/tailscale.js`: typed event emitter wrappers over `child_process`. Use `NodeJS.EventEmitter` as the base.
- `oauth/services/*.js`: each provider has its own token-refresh contract. Define `OAuthProvider` interface with `refresh(credentials: unknown): Promise<RefreshedCredentials>`.
- `sqlite/connection.js`: the singleton is exposed via `getDatabase(): Database` where `Database` is `better-sqlite3`'s type. `tx(fn: (db: Database) => T): Promise<T>`.

**Risks**:

- `localDb.js` is 1663 lines. The conversion will surface many implicit `any` in SQL row mappings. Strategy: introduce `DbRow` and `DbResult<T>` types, then convert row-by-row. Do not try to type every query in one pass.
- `localDb.js` contains `isCloud` runtime branch using `typeof caches !== "undefined"`. Add a `declare const caches: CacheStorage | undefined` to `src/types/global.d.ts` so TS knows about the Cloudflare global.
- The `import.meta.url` / `createRequire` pattern in `sqlite/connection.js` is fine in TS; no special handling.

**Exit criteria**:

- All `src/lib/**` files are `.ts` / `.mts`.
- `tsc --noEmit` clean.
- All 1338 tests pass.
- `localDb.js`'s public API has named types in `src/lib/localDb.types.ts` (or co-located).
- 0 `as any` introduced.

**Effort**: large (1–2 weeks; the bulk of the work).

## Phase 4 — API route handlers

**Goal**: type the HTTP surface end-to-end.

**Scope**: every file under `src/app/api/**/route.js`. Route groups (26, verified): `auth, cache, cloud, combos, health, init, keys, media-providers, memory, models, monitoring, oauth, pricing, provider-nodes, providers, proxy-pools, restart, settings, shutdown, tags, translator, tunnel, usage, v1, v1beta, version`. Plus `src/app/callback/**` for OAuth callbacks.

**tsconfig strategy**: still `checkJs: false` globally. The `.ts` files are checked; JS consumers from `src/lib/**` are not.

**Type strategy**:

- For every `route.js` with `export async function POST(request: NextRequest)`:
  - Parse body with the now-typed `parseJsonBody(request): Promise<[unknown, NextResponse | null]>`.
  - Narrow the body inline with a `zod`-like guard or hand-written type guard. The codebase does not use zod today; do not introduce it. Use `isRouteRequest(value): value is RouteRequest` functions in `src/lib/apiGuards.ts` (new file in this phase) — one per route family.
  - Return types: `NextResponse<ApiResponse<T>>` where `ApiResponse<T> = { ok: true; data: T } | { ok: false; error: string }`.
- Streaming routes (`/api/v1/chat/completions`, `/api/monitoring/health/stream`) keep returning `Response` with `ReadableStream<Uint8Array>` body. The TypeScript types for `ReadableStream` are stable in `lib.dom.d.ts`.
- Health checks (`/api/health`, `/api/monitoring/health*`) are simple and easy.
- `/api/v1/*` and `/api/v1beta/*` are OpenAI / Gemini compatible — define `OpenAIChatRequest`, `OpenAIChatResponse`, `GeminiGenerateRequest`, etc., in `src/app/api/v1/_types.ts`. Reuse these from `src/sse/handlers/chat.ts` (Phase 5).

**Risks**:

- Many route handlers are "thin" and just forward to `lib/`. They get typed almost for free.
- Some routes use `request.text()` directly (e.g. for streaming bodies). Type the body as `string` and let the consumer `JSON.parse` it with `unknown` and narrow.
- The 100-connection SSE cap is enforced downstream; route types don't care.

**Exit criteria**:

- All `src/app/api/**/route.js` files converted.
- `src/app/api/v1/_types.ts` and equivalents exist and are imported by the relevant routes.
- `tsc --noEmit` clean.
- All 1338 tests pass.
- `bun run build` produces a working standalone bundle.

**Effort**: large (1–2 weeks; mostly mechanical).

## Phase 9 — `open-sse/` decision

`open-sse/` is a local engine fork (AGENTS.md rule: "Never replace local open-sse with the npm package"). It is also the most dynamic, type-hostile part of the codebase: heavy use of `any`-shaped data from upstream providers, Web Streams transformations, polymorphic `executor` dispatch, translator pipelines.

Three options, in preference order:

1. **Recommended: freeze `open-sse/` as JS.** Convert only the **ambient declarations** in `src/sse/open-sse.d.ts` (Phase 5) to describe the public API. Add a `tsconfig.exclude` entry to make it explicit. Reasons: high migration cost, low day-to-day churn from this repo (it's a fork synced from upstream), most of its surface is consumed through `src/sse/` which is now fully typed.
2. **Convert incrementally with `allowJs: true` only.** Same shape as the main app. Useful if the fork starts seeing internal feature work. The translator and handler cores still need `any`-grade escape hatches for the streaming transforms.
3. **Skip entirely.** Same as (1) but without the ambient `.d.ts`. Callers use `unknown` and cast at use sites. Worst of both worlds.

**Exit criteria** (assuming option 1):

- Documented in `.agents/plan/js-to-ts-migration.md` (this file) under "Final State".
- `tsconfig.json` excludes `open-sse/**` explicitly.
- `src/sse/open-sse.d.ts` exists and is referenced from `src/sse/**` (it should be, after Phase 5).
- AGENTS.md "Project Identity" updated to: `Bun + Next.js 16 + TypeScript (src/, cloud/), open-sse fork stays JS`.

**Effort**: small (decision + docs).

## Risks Specific to This Project

1. **Dynamic proxy patterns in `open-sse/handlers/chat.js` and `open-sse/translator/`** — not in scope (Phase 9 freezes as JS). The TS path interacts only through `src/sse/open-sse.d.ts`. If `open-sse/` is later migrated, expect significant `any` use at provider boundaries.
2. **Web Streams / `TransformStream` API surface** — `lib.dom.d.ts` covers `ReadableStream`, `WritableStream`, `TransformStream`, `TransformStreamDefaultController`. The codebase uses these in `src/sse/` (readable stream pumps) and `open-sse/translator/` (transform pipelines). For `open-sse/`, freezing as JS sidesteps the question.
3. **Bun-specific globals** — `Bun.RedisClient` (used in `src/lib/rateLimit/redis.js`), `Bun.serve` (not currently used in the main app but available), `bun:sqlite` (used via `next.config.mjs`'s `serverExternalPackages: ["bun:sqlite"]`). `@types/bun` covers all of these. The `bun:sqlite` import in `src/lib/sqlite/connection.js` does not have its own type declarations; use `// @ts-expect-error bun:sqlite has no upstream types` or add a `src/types/bun-sqlite.d.ts` ambient declaration.
4. **next.config / JSX** — Next.js 16 + TS is well-trodden. No special handling. `next-env.d.ts` is auto-generated.
5. **Bun import attributes** — `import pkg from "../../../package.json" with { type: "json" }` is supported in TS 5.3+ via `--moduleResolution bundler`. We have `bundler` set. Confirmed.
6. **Biome formatter vs. TypeScript syntax** — Biome 2.4 supports TS. Watch for: optional chaining `?.`, nullish coalescing `??`, template literal types, and `as const` assertions. Run `biome format --write` after each migration PR to catch formatting drift.
7. **Standalone build** — `output: "standalone"` traces JS imports. After migrating to `.ts`, verify `bun run build` still produces a self-contained `.next/standalone/` directory. The `serverExternalPackages: ["bun:sqlite"]` config is unaffected.
8. **Cloud Worker compile** — `wrangler` uses esbuild, not tsc. We add `tsc` to `cloud/` only as a check, not as the build pipeline. The Worker continues to be built by `wrangler deploy`.
9. **`package.json` `with { type: "json" }`** — the codebase uses this in `src/shared/constants/config.js`. TS 5.3+ understands it under `moduleResolution: "bundler"`. If TS errors, fall back to `resolveJsonModule: true` (already set) and switch the import to `import pkg from "../../../package.json"`.
10. **Test count drift** — we add new tests (type tests, matcher-drift test) but must not delete any of the existing 1338. The verification step `bun run test:run` reports the test count; the PR description must call out "+N new tests, total 1338+N".

## Rollback Strategy

Each phase is a single PR. If a phase's `tsc --noEmit` or test suite fails in a way that can't be fixed in the same PR, revert the PR. No cross-phase dependencies in the runtime sense — the only cross-phase dependency is that later phases assume earlier files are `.ts` for the path imports to work, but a `.js` import of a `.ts` file would just fail to build. Therefore: if a later phase is rolled back, the earlier-converted file is also `.ts`, and JS callers still find it via Bun's resolution.
